# Agent and harness integration

CCS offers a JSON CLI, a standard-library Python client and an optional stdio MCP server. All three use the same gateway classification, capability checks, plan confirmation and audit records. They do not change the worker deployment or grant the caller additional SSH permissions.

Examples use editable placeholder paths and worker identifiers. Replace them with your local configuration. Keep passwords and private-key content outside requests and harness configuration; the CCS command can reference your existing SSH configuration and pinned host-key file.

## Installation and command prefix

From the CCS directory, with Python 3.11 or later:

```powershell
python -m pip install -e .
```

The Python client has no third-party dependencies. The optional MCP adapter requires MCP SDK 2.2 or later within the 2.x series (`mcp>=2.2,<3`):

```powershell
python -m pip install -e '.[mcp]'
```

The command prefix is a JSON array of arguments or a Python sequence. It includes the executable and all gateway configuration flags, but excludes `request --file -`; the client appends those arguments and writes UTF-8 request JSON to standard input. CCS does not parse a command string or invoke a shell.

Installed CLI prefix:

```json
["ccsctl", "--fleet", "config/worker-pool.json", "--db", "data/orchestrator.db", "--audit-db", "data/ccs-audit.db"]
```

PowerShell project-wrapper prefix:

```json
["pwsh", "-NoProfile", "-File", "C:/path/to/project/scripts/ccs.ps1"]
```

Use your project's wrapper when it fixes the worker pool, SSH identity or host keys. `cwd` resolves relative CLI configuration paths on the local computer; it is not a remote working-directory setting.

## Python client

Before constructing task payloads, query the installed contract without contacting a worker:

```python
client = CCSClient(["ccsctl"])
print(client.describe("run.submit"))
print(client.describe("workspace.execute", workspace_action="stage"))
```

`ccsctl describe` and `gateway.describe` work without a host, fleet, SSH identity or runtime database.
CLI schema queries and the MCP action lists come from the same packaged contract as gateway validation.
MCP clients can use `ccs_read(action="gateway.describe", payload={"action":"run.submit"})`.
See the [generated action reference](ACTION-CONTRACTS.md) for every action and workspace sub-action.
Invalid fields fail locally with `field_errors` entries containing a field path, code and message.
`CCSError.field_errors` and `to_dict()` retain that information; field values are not echoed in errors.

Standalone release and the separate core/MCP/research verification commands are documented in
[the release workflow](RELEASING.md). A core pass does not establish optional MCP or Linux readiness.

```python
from ccs.client import CCSClient, CCSError

client = CCSClient(
    [
        "ccsctl", "--fleet", "config/worker-pool.json",
        "--db", "data/orchestrator.db", "--audit-db", "data/ccs-audit.db",
    ],
    cwd="C:/path/to/CCS",
    timeout=120,
    actor_id="my-harness",
    actor_kind="service",
)

try:
    workers = client.request("fleet.status", {}, dry_run=False)
    print(workers)
except CCSError as exc:
    print(exc.code, exc.message, exc.retryable, exc.request_id)
```

`request(action, payload, *, dry_run=True, request_id=None, confirm_plan_sha256=None)` returns the gateway's `data` object. Omitting `dry_run` prepares a plan. An omitted request ID is generated by the client. `CCSError` exposes `code`, `message`, `retryable`, `request_id`, `execution_state`, `operation_id`, `worker_id`, `run_id` and `idempotency_key` for gateway or client failures. Correlation fields may be `None` when no identity or receipt is known. `exc.to_dict()` returns the same metadata contract used by CLI and MCP errors.

`plan(action, payload, *, request_id=None)` returns a `CCSPlan` with `request`, `data` and `plan_sha256`. The request contains the actor and original payload required for confirmation. `confirm(plan)` submits that request with `dry_run=False` and its plan digest; it does not invent a new request identity or choose a different worker.

Prepare a proposed run using an existing ExperimentSpec, without starting training:

```python
import json
from pathlib import Path

spec = json.loads(Path("examples/agent-smoke-spec.json").read_text(encoding="utf-8"))
plan = client.plan("run.submit", {
    "worker_id": "my-worker",
    "spec": spec,
    "idempotency_key": "my-proposed-run-v1",
})
print(plan.data)
print(plan.plan_sha256)
```

The [smoke spec](../examples/agent-smoke-spec.json) runs a short Python standard-library command without requesting a GPU. Adjust `python3` to an interpreter available on your worker. Replace it with your own ExperimentSpec for real work; see [the request protocol](CCS-AGENT-INTERFACE.md).

After the caller has obtained the required approval or verified that the proposed action is within an existing authorization, execution is a separate call:

```python
result = client.confirm(plan)
```

Changing the request ID, actor, action, payload or worker invalidates the original digest. A plan digest binds those fields; it is not a signature, a user login or proof of approval. `actor_id` and `actor_kind` are audit metadata under the current trusted-local-caller model.

The [runnable Python example](../examples/python-client.py) defaults to `fleet.status`. It accepts `--command-json` so paths and flags remain separate arguments:

```powershell
python .\examples\python-client.py `
  --command-json '["ccsctl","--fleet","config/worker-pool.json","--db","data/orchestrator.db","--audit-db","data/ccs-audit.db"]' `
  --cwd 'C:/path/to/CCS'
```

Add `--plan-submit --spec SPEC.json --worker-id my-worker --idempotency-key my-proposed-run-v1` to print a submission plan. This example never calls `confirm` and never starts training.

## MCP over stdio

The optional `ccs-mcp` entry point starts a stdio server:

```powershell
ccs-mcp `
  --command-json '["ccsctl","--fleet","config/worker-pool.json","--db","data/orchestrator.db","--audit-db","data/ccs-audit.db"]' `
  --cwd 'C:/path/to/CCS' --timeout 120 --actor-id mcp-agent
```

The [MCP configuration example](../examples/mcp-server.json) uses absolute Python/module launchers and starts in read-only mode. Replace all placeholder paths with the installed environment and local configuration. A harness running elsewhere needs its own local CCS installation and SSH credentials.

When using source without installing the CCS package, install the optional MCP dependency into the selected Python environment, set `PYTHONPATH` to the absolute CCS `src` directory, and replace the server command with `python -m ccs.mcp_server`. The same command-line flags apply:

```powershell
$env:PYTHONPATH = 'C:/path/to/CCS/src'
python -m ccs.mcp_server `
  --command-json '["pwsh","-NoProfile","-File","C:/path/to/project/scripts/ccs.ps1"]' `
  --cwd 'C:/path/to/project'
```

The server fixes `actor_id` from its startup flag and uses `actor_kind="agent"`. Tool calls do not accept an actor override. By default it exposes three tools; `--read-only` exposes only `ccs_read` and rejects all mutations, including workspace stage/apply/restore/discard:

| Tool signature | Purpose |
|---|---|
| `ccs_read(action, payload)` | Execute a classified read-only action, including read-only `workspace.execute` subactions. |
| `ccs_plan(action, payload, request_id=None)` | Prepare a mutation plan, retaining the request identity, actor, payload and digest. |
| `ccs_execute(action, payload, request_id, plan_sha256)` | Execute a previously prepared mutation plan after the caller's approval policy permits it. |

`ccs_read` accepts `fleet.status`, `worker.health`, `worker.monitor`, `worker.alerts`, `worker.storage`, `worker.processes`, `run.snapshot`, `run.events`, `run.logs`, `run.artifacts`, `gateway.audit`, `operation.query`, `operation.reconcile` and the permitted read-only workspace subactions. `operation.reconcile` reads the original worker and can update the local operation ledger; it performs no remote mutation. `ccs_plan` and `ccs_execute` accept `run.submit`, `run.cancel`, `checkpoint.replicate`, `checkpoint.import` and `workspace.execute`. Payloads retain the existing [gateway protocol](CCS-AGENT-INTERFACE.md).

Start with these arguments to `ccs_read`:

```json
{"action": "fleet.status", "payload": {}}
```

All five worker diagnostic actions accept an explicit worker identity:

```json
{"action": "worker.health", "payload": {"worker_id": "my-worker"}}
```

The response identifies the actual worker in `data.result.worker_id`. Empty payloads keep the configured legacy default adapter. Disabled workers remain available for diagnostics while new Run submission stays blocked. Unknown worker identities fail without falling back to another machine.

For a proposed submission, pass the `spec` object loaded from an existing ExperimentSpec file in the Python example above to `ccs_plan`:

```python
plan_arguments = {
    "action": "run.submit",
    "payload": {
        "worker_id": "my-worker",
        "spec": spec,
        "idempotency_key": "my-proposed-run-v1",
    },
    "request_id": "my-submission-plan-001",
}
```

Successful `ccs_plan` calls return a structured envelope with `ok=True`, `data={"request": original_request, "plan": gateway_plan_data}` and `error=None`. Read or execute success places the gateway data directly in `data`. The same JSON envelope is also returned in the text content block. When using the MCP Python SDK, the structured envelope is available as `CallToolResult.structured_content`.

After reviewing `data.plan`, including `executable`, and obtaining authorization, construct the `ccs_execute` arguments from the returned plan envelope:

```python
# planned is the structured envelope returned by ccs_plan.
request = planned["data"]["request"]
execute_arguments = {
    "action": request["action"],
    "payload": request["payload"],
    "request_id": request["request_id"],
    "plan_sha256": planned["data"]["plan"]["plan_sha256"],
}
# Send execute_arguments to ccs_execute only when authorization permits it.
```

Failures set `CallToolResult.is_error=True` and return `ok=False`, `data=None` and an `error` object with the `CCSError.to_dict()` metadata above. MCP schema errors can be reported by the MCP SDK before a CCS gateway call is made.

Read-only workspace subactions are `inspect`, `diff` and `changes`. `stage`, `apply`, `restore` and `discard` require planning and execution confirmation. See [workspace constraints](REMOTE-WORKSPACE.md).

The MCP server does not approve operations automatically. `ccs_execute` uses the original request and digest; altering plan fields invalidates confirmation. A harness must enforce the user's approval or prior authorization before calling it. Connecting the server is not permission to submit, cancel or modify tasks.

There is no server-side plan cache. A harness can retain the four execution arguments across a server restart, provided the configured actor, command and working directory remain consistent. CCS revalidates the digest and current gateway requirements when executing; retaining a plan does not bypass changed capabilities, inputs or routing constraints.

Only stdio transport is provided. The existing loopback dashboard remains a separate read-only HTTP service. These adapters do not provide remote HTTP execution, network user authentication, a multi-tenant service or isolation for untrusted code.

## Errors, retries and execution evidence

The client timeout bounds the local CLI exchange; it is not a training time budget or a remote cancellation request. A timeout while executing a mutation reports `execution_state="unknown"` and `retryable=False`: the worker may already have accepted it. Keep the original request identity, worker, key and plan; do not create another key or select another worker to retry an uncertain change.

First read the durable local ledger, then reconcile a submission if needed:

```python
operation = client.request(
    "operation.query", {"idempotency_key": "my-proposed-run-v1"}, dry_run=False,
)
print(operation["result"])
reconciled = client.request(
    "operation.reconcile", {"idempotency_key": "my-proposed-run-v1"}, dry_run=False,
)
print(reconciled["result"])
```

Both payloads require exactly one of `operation_id`, `idempotency_key` or `request_id`. A request ID can be ambiguous across actors; prefer the operation ID or submission key. `operation.query` makes no SSH call. `operation.reconcile` currently supports only `run.submit`; it reads acceptance by key from the recorded worker and persists local confirmation without dispatching another Run. Missing lookup capability, connection failure or an absent lookup result keeps the outcome unknown. Local `OPERATION_NOT_FOUND` is not evidence that a request sent using another database never executed.

Successful mutation data includes `operation` and `execution_state`; `confirmed` means the mutation response is confirmed, and for submission means the Run was accepted rather than completed. A final audit failure returns the successful result with an `AUDIT_UNAVAILABLE` warning. Use durable operation state, not an absent audit entry or `retryable`, to decide what is known. Generic mutations record their identity and block duplicate execution after dispatch begins; cancellation, workspace and checkpoint recovery require the action-specific observations in [the operation guide](P0-03-OPERATIONS.md).

If audit database initialization fails, read-only calls and dry-runs remain available with `AUDIT_UNAVAILABLE` warnings, including local operation queries. Confirmed mutation requests are blocked before dispatch while pre-dispatch audit is unavailable.

Atomic submission admission covers callers sharing the same controller database. Controllers using separate databases do not receive a global cross-worker idempotency guarantee. Worker diagnostic routing and the local admission gate need no worker upgrade; automated uncertain-submission reconciliation requires a worker declaring `run.lookup=1`. Deploying that worker capability is a separate action.

Keep read-only observations separate from execution evidence. A stale `RUNNING` record does not prove a process is still running. A successful checkpoint import verifies transfer, not that a compatible model actually restored and continued optimizer updates. CCS manages independent runs across a worker pool; a single run spanning multiple machines with NCCL or DeepSpeed is not currently coordinated.

For guarantees and limits, see [capability negotiation](CAPABILITY-NEGOTIATION.md), [multi-worker coordination](MULTI-WORKER.md), [checkpoint transfer](CHECKPOINT-REPLICATION.md) and [model recovery adapters](MODEL-RECOVERY-ADAPTERS.md).

## Bounded reads and local waiting (0.6.0)

Use `limit` or `max_bytes` to enable `run.events`/`run.artifacts` pagination. The defaults are 100 items and 1 MiB of UTF-8 item-array data; maximums are 1000 items and 16 MiB. Responses add `next_cursor`, `has_more`, and `truncated`. Continue events with `after_seq=next_cursor`, or artifacts with `cursor=next_cursor`. A cursor advances only through returned items. A first item too large for the budget fails with `PAGE_ITEM_TOO_LARGE`; increase the budget or narrow the selection. Envelope overhead is subject to the transport's separate 20 MiB limit. Old requests without page options retain their collection format, and an oversized legacy response fails explicitly instead of being silently shortened.

Paged reads require workers declaring `run.events.page=1` or `run.artifacts.page=1`. There is no silent fallback to unbounded reads. Artifact cursors bind the run and path filter; the inventory is live and ordered by path. A new path below the cursor requires a fresh scan. Event JSONL gains a disposable SQLite byte-offset index: existing files are indexed once, then reads and appends index only the tail. A partial final line is not delivered; append quarantines it before publishing the next complete event. Controller watermarks are migrated and committed with remote events, so a restart does not scan the entire controller history.

`fleet.status` runs at most four observations in parallel. Its optional `timeout_seconds` (default 10) and `worker_timeout_seconds` (default 5) are finite budgets from 0.01 to 60 seconds. A slow worker reports `WORKER_OBSERVATION_TIMEOUT`; workers that could not obtain a bounded slot report `WORKER_OBSERVATION_BUSY`. These reads never alter worker selection or cancel training.

```python
from ccs import CCSClient, CCSPlan, CCSReadCursor

# Save the exact plan for another client process; an existing file is not replaced.
plan.save("submission-plan.json")
restored = CCSPlan.load("submission-plan.json")
# client.confirm(restored) remains an explicit mutation within the caller's authority.

position = CCSReadCursor("run.events", "run_example", worker_id="worker-a")
for event in client.iter_events("run_example", worker_id="worker-a", cursor=position,
                                total_timeout=30, limit=100, follow=False):
    consume(event)
    persist(position.to_dict())
# Reconnect with CCSReadCursor.from_dict(saved_position).

snapshot = client.wait_run("run_example", worker_id="worker-a", total_timeout=60)
for chunk in client.iter_logs("run_example", worker_id="worker-a", total_timeout=30):
    print(chunk["text"], end="")
```

The cursor records items delivered by the iterator, including a page's delivered prefix. It is not an acknowledgment that application processing or persistence succeeded: persist after successful consumption, or keep the last acknowledged cursor yourself. `follow=True` waits within the total deadline; the event iterator drains again after seeing a terminal snapshot. Log iteration uses the existing byte-offset/rotation protocol.

`CCSClient` defaults to four active gateway subprocesses and eight queued requests (`max_concurrent`, `max_queued`). MCP defaults to two active calls and eight queued calls, configurable via startup flags. Overload returns `GATEWAY_BUSY` or `MCP_BUSY`; queued cancellations do not launch a child. Passing `cancel_event=threading.Event()` lets a caller stop its local exchange or wait. `WAIT_TIMEOUT`/`WAIT_CANCELLED` never call `run.cancel`. An already-started mutation stopped by timeout, cancellation, or an output limit remains `execution_state="unknown"`, with no automatic retry. Local gateway/SSH subprocess trees are terminated and pipe buffers stay bounded (default 20 MiB stdout, 64 KiB stderr). `GATEWAY_OUTPUT_LIMIT` reports `output_truncated` and continuation advice; resume reads with the last delivered cursor, and reconcile mutations by their original identity.

MCP `--read-only` registers only `ccs_read`. Repeatable `--allow-action` flags narrow actions, for example `--allow-action gateway.describe --allow-action run.logs`. Workspace access still checks the nested action; allowing `workspace.execute` in read-only mode permits only inspect/diff/changes. Cancellation of an active MCP call signals its client subprocess, and its concurrency slot remains occupied until cleanup finishes. These startup guards constrain a trusted local integration; they are not authentication, multi-tenant authorization, or isolation from arbitrary programs that already have SSH access.

## Offline doctor and configuration preview

```powershell
ccsctl doctor --python 'C:/path/to/venv/Scripts/python.exe' --require-mcp `
  --command-json '["C:/path/to/venv/Scripts/python.exe","-m","controller.gateway_cli","--fleet","C:/path/to/project/config/worker-pool.json"]' `
  --cwd 'C:/path/to/project'

ccsctl mcp-config --python 'C:/path/to/venv/Scripts/python.exe' `
  --command-json '["pwsh","-NoProfile","-File","C:/path/to/project/scripts/ccs.ps1"]' `
  --cwd 'C:/path/to/project' --output 'C:/path/to/project/mcp-new.json'
```

`doctor` checks local paths, Python >=3.11, an optional MCP >=2.2,<3 dependency, and an optional existing `--mcp-config` structure. It does not execute the configured gateway, read private-key content, create runtime databases, or contact workers. Explicit remote probing uses `ccsctl --fleet CONFIG doctor --probe-remote --worker-id ID`, which performs only worker health reading. Missing programs, invalid cwd, absent entry scripts, and incompatible dependencies return actionable diagnostic codes.

`mcp-config` previews concrete target/content/digest, using absolute paths and default `--read-only`. To create that exact new file, repeat the same command with `--write --confirm-sha256 DIGEST`. Existing files are never overwritten; parent directories must already exist. Use `--allow-mutations` only when the integration needs the mutation tools. Generated configuration references interpreter and key paths; it does not contain private-key bytes. The digest guards the reviewed configuration content, not user authentication.

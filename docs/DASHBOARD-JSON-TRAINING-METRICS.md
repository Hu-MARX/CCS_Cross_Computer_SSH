# Read-only JSON training metrics bridge — 2026-09-09

Root cause: the active SparseCoop launcher emits training_launch/training_progress JSON to stdout, but does not populate the standard worker progress sampler. Its dashboard configuration evidence had not been generated. The live API reproduced configuration=not_recorded,loss=null,points=0.

Using the diagnosing-bugs regression workflow, added an opt-in primary-Run bridge. It invokes the versioned CCS JSON run.logs read action through gateway_cli, with explicit worker,strict host keys,and a persisted byte cursor. A separate30-second local collector prevents browser requests from issuing SSH calls. At most262144bytes per poll; partial lines survive restarts; up to6000points retain the full time span by thinning older points. A matching training_launch effective-config digest is required before interpreting metrics. Nonfinite values and mismatched Run/config/cursor fail closed.

The supplement never changes server state or replaces lifecycle/health with log-derived guesses. Existing native progress takes precedence. The graph uses actual logged step/loss and observed LR minimum/maximum (not reconstructed optimizer-group identities). Timestamps are explicitly local collection times,not training-event timestamps. Nominal epoch is derived from logged updates/1377. Standard worker freshness remains separate from metric collection freshness. Full optimizer-group state and checkpoint telemetry are still unreported,not invented.

`research/scripts/build_sparsecoop_dashboard_config.py` generates28 source-hashed submitted configuration entries bound to the actual Run/spec. Sources stay local in ignored config-evidence storage; the generator and implementation are reviewable. This does not treat an approved setting as a new live optimizer observation.
